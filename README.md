# 1Password Custom Field Autofill Matching Lab

1Password のカスタムフィールドが、DOM 上のどの識別情報（`id` / `name` / `placeholder` / `label` / ARIA 属性 / 周辺テキストなど）と一致したときに Autofill されるのかを、ブラックボックスで検証するための単一 HTML ページです。

ビルド不要・依存パッケージなしで、[index.html](index.html) をブラウザで開くだけで動作します。

## 検証の仕組み

- ページ内に、識別情報の与え方だけを変えた入力フィールドを多数配置しています
- 1Password 側にカスタムフィールド **`OP_TEST_TOKEN`** = **`FILLED_BY_1PASSWORD`** を用意し、このページで Autofill を実行します
- 各フィールドについて、以下のいずれかを満たしたものを「一致した（ヒット）」とみなします
  - 値が `FILLED_BY_1PASSWORD` になっている
  - 1Password が付与する `data-com-onepassword-filled` 属性が付いている
- ヒットしたフィールドは枠線でハイライトされ、各行の右側に属性のスナップショットが JSON で表示されます

> [!IMPORTANT]
> 実測では、1 回の Autofill で埋まるのは**カスタムフィールド 1 つにつき 1 フィールドのみ**でした。
> つまり「埋まらなかった = マッチしなかった」とは断定できません。マッチはしたが選ばれなかっただけの可能性があります。
> 属性ごとの判定を確実に取るには、1 ケースだけを残して他を取り除いた状態で 1 回ずつ試す必要があります（[実験モード](#実験モードurl-パラメータ)の `?only=` を使ってください）。

## 使い方

### 1. 1Password 側の準備

1. 任意のログインアイテム（このページのドメイン／ファイルに紐づくもの）を開く
2. カスタムフィールドを追加する
   - 種類: **Text**
   - ラベル: `OP_TEST_TOKEN`
   - 値: `FILLED_BY_1PASSWORD`
3. 保存する

### 2. ページを開く

```bash
open index.html
```

`file://` で開いた場合に拡張機能が動作しないときは、ローカルサーバー経由で開いてください。

```bash
python3 -m http.server 8000
# → http://localhost:8000/
```

### 3. Autofill して結果を見る

1. 1Password の拡張機能から Autofill を実行する
2. 「結果を再スキャン」を押す（属性変化は MutationObserver でも自動検知されます）
3. ページ上部のサマリと、各行の JSON でどのフィールドがヒットしたかを確認する

## 実験モード（URL パラメータ）

「1 回の Autofill で 1 フィールドしか埋まらない」という制約を回避し、選定基準を切り分けるためのモードです。
いずれも **1Password がフィールドを走査するより前**に DOM を確定させる必要があるため、URL パラメータとして読み込み時に適用されます。読み込み後に JS で操作するボタンでは代用できません。

| パラメータ | 動作 | 用途 |
| --- | --- | --- |
| `?only=<ケースID>` | 指定ケース以外の `.case` を DOM から**削除**し、input を 1 つだけ残す | 属性ごとのマッチ有無を単独で判定する |
| `?reverse=1` | 各セクション内のケース順を読み込み時点で反転する | 位置ベース説の検証。反転時は `7-A` がページ最後の input になる |

併用可能です（例: `?only=7-A&reverse=1`）。ケース ID は `0-A` 〜 `7-C` で、ページ上部のモードパネルにある「1ケースだけを残して開く」から全 31 件のリンクを辿れます。存在しない ID を指定した場合は全ケース表示にフォールバックし、警告を表示します。

```
index.html?only=1-C          # placeholder一致のケースだけを残す
index.html?only=2-A          # label for のケースだけを残す
index.html?reverse=1         # 全ケースを読み込み時点で逆順にする
```

> [!TIP]
> 単独モードで 1 ケースずつ試すと、「マッチする属性の一覧」が確定します。これが分かってから `?reverse=1` で位置の影響を見ると、結果を解釈しやすくなります。

## ツールバー

| ボタン | 動作 |
| --- | --- |
| 結果を再スキャン | 全フィールドを再判定して表示を更新する |
| 入力値をクリア | 値と `data-com-onepassword-filled` を消して初期状態に戻す |
| DOM順を反転（読み込み後） | セクション内の行順を逆にする。**読み込み後**の並べ替えなので、1Password が読み込み時に構築した索引には反映されない可能性がある。tie-break の検証には `?reverse=1` を使うこと |
| 結果JSONをコピー | モード情報・UserAgent・全フィールドの属性スナップショットをクリップボードにコピーする |

## テストケース一覧

| セクション | 検証内容 |
| --- | --- |
| 0. Baseline / DOM順 | 識別情報を持たない通常 input。誤爆や DOM 順だけでの充填が起きないかの基準 |
| 1. 直接属性 | `id` / `name` / `placeholder` / `title` の一致 |
| 2. label | `label for` / label 内包 / 関連なし label / 壊れた `for` / DOM 上離れた `for` |
| 3. ARIA | `aria-label` / `aria-labelledby` / `aria-describedby` |
| 4. 周辺テキスト / Tooltip | 直前の `span` / `div`、CSS ツールチップ、`hidden` テキスト |
| 5. 要素 / input type | `textarea` と `type=text/search/email/password` の差 |
| 6. form / autocomplete | form 内外の差、`autocomplete=off` / `autocomplete=username` |
| 7. 完全重複候補 | 同一の識別情報を持つ 3 フィールド。tie-break が DOM 順かの確認 |

## 結果の記録

「結果JSONをコピー」で取得できる JSON は次の形です。実行モードと UserAgent が含まれるため、条件込みでそのまま保存できます。

```jsonc
{
  "mode": { "only": "1-C", "reverseAtLoad": false },
  "userAgent": "...",
  "fields": [
    {
      "case": "1-C", "tag": "input", "type": "text",
      "id": "placeholder-test", "name": "placeholder_test",
      "placeholder": "OP_TEST_TOKEN", "labels": [],
      "value": "FILLED_BY_1PASSWORD",
      "onePasswordFilled": "light", "domIndex": 0
      // title / ariaLabel / ariaLabelledby / ariaDescribedby / autocomplete も含む
    }
  ]
}
```

JSON に含まれないため、別途記録しておくと有用な条件:

- 1Password 拡張機能のバージョン
- OS
- Autofill の実行方法（ショートカット / 拡張機能のポップアップ / インラインアイコン）

## 観測された挙動

### 全ケースを 1 ページに並べた状態での Autofill

**結果: `7-C duplicate #3` のみに値が入り、他の全フィールドは空のまま。**

読み取れること:

- 1 回の Autofill で充填されるのは 1 フィールドのみ。複数の候補がマッチしても 1 つに絞られる
- 選ばれたのはページ内で**最後**の input であり、かつ `placeholder` と `aria-label` の**両方**がマッチする唯一のグループ（7-A/B/C）の一員だった

### 「各セクションのDOM順を反転」後に再度 Autofill

**結果: 反転後も `7-C duplicate #3` のみに値が入った。**

反転によりセクション 7 の並びは 7-C → 7-B → 7-A となり、7-C は先頭、**7-A がページ最後の input** になります。
それでも 7-C が選ばれたため、「ライブ DOM 順で最後のものが選ばれる」という単純な位置ベース説は成立しません。

ただしこの試行には交絡があり、**説を棄却する根拠にはなりません**:

- 反転ボタンは JS で `appendChild` し直しているだけで、1Password はページ読み込み時にフィールドを走査してインデックスを保持している可能性が高い
- その場合、後から並べ替えても拡張機能側の認識は更新されず、「読み込み時の DOM 順で最後」のまま 7-C が選ばれ続ける

### 単独モード（`?only=`）による属性別の判定

31 ケースを 1 件ずつ単独で実行した結果。**✓ = 充填された / ✗ = 充填されなかった**。

| ケース | 内容 | 結果 |
| --- | --- | :---: |
| 0-A / 0-B / 0-C | 識別情報なしの通常 input | ✗ |
| 1-A | `id` 一致 | ✓ |
| 1-B | `name` 一致 | ✓ |
| 1-C | `placeholder` 一致 | ✓ |
| 1-D | `title` 一致 | ✓ |
| 2-A | `label for` | ✓ |
| 2-B | label 内包 | ✓ |
| 2-C | 関連なし label | ✓ |
| 2-D | 壊れた `for` | ✓ |
| 2-E | 離れた `for` | ✓ |
| 3-A | `aria-label` | ✓ |
| 3-B | `aria-labelledby` | ✓ |
| 3-C | `aria-describedby` | ✗ |
| 4-A | `span` 直前 | ✓ |
| 4-B | `div` 直前 | ✓ |
| 4-C | CSS tooltip（`display:none`） | ✗ |
| 4-D | `hidden` テキスト | ✗ |
| 5-A | `textarea` + `placeholder` | ✗ |
| 5-B | `type=text` + `placeholder` | ✓ |
| 5-C | `type=search` + `placeholder` | ✗ |
| 5-D | `type=email` + `placeholder` | ✗ |
| 5-E | `type=password` + `placeholder` | ✗ |
| 6-A | form 内 | ✓ |
| 6-B | form 外 | ✓ |
| 6-C | `autocomplete=off` | ✓ |
| 6-D | `autocomplete=username` | ✓ |
| 7-A / 7-B / 7-C | 完全重複候補 | ✓ |

### 単独モードから読み取れること

**1. 要素の型が「門番」として働いている**

5 系はすべて `placeholder="OP_TEST_TOKEN"` で識別情報が同一なのに、`type=text` の 5-B だけが充填されました。`search` / `email` / `password` と `textarea` は全滅です。
つまり型は**マッチのシグナルではなく、充填可能かどうかを決めるゲート**として働いています。`type` 属性を持たない 1-C（＝暗黙の `text`）が有効なこととも整合します。Text カスタムフィールドの投入先は実質 `input[type=text]` に限られる、と読めます。

**2. ラベル探索の範囲は正式な関連付けより広い**

`id` / `name` / `placeholder` / `title` / `aria-label` / `aria-labelledby` に加えて、**関連付けが成立していないケースまで有効**でした。

- 2-C（`for` も内包もない単なる label）
- 2-D（`for` が存在しない ID を指す壊れた label）
- 4-A / 4-B（直前の `span` / `div` のテキスト）

DOM 上の正式な紐付けを辿っているのではなく、**近傍の可視テキストを拾っている**と考えられます。2-E（DOM 上は離れているが `for` は正しい）も有効なので、正式な関連付けも併用されています。

**3. 不可視テキストは対象外**

4-C（`display:none` の tooltip テキスト）と 4-D（`hidden` 属性）はいずれも無効。テキストの内容は一致しているため、**可視性でフィルタしている**ことが分かります。

**4. `aria-describedby` はラベル情報源として使われていない**

3-C のみ無効でした。単独モードで検証しているため、他フィールドとの競合による取りこぼしではありません。

`aria-describedby` は ID による明示的な参照なので、仮に採用されていれば参照先 span が input の前後どちらにあっても解決されます（3-B の `aria-labelledby` が有効だったのと同じ理屈）。それでも充填されなかったため、**`aria-describedby` はラベル情報源として扱われていない**と確定します。

なお 3-C の span は input の**後ろ**にありますが、これは上記の結論には影響しません。「ARIA を伴わない後方の可視テキストを拾うか」は別問題として未検証です（4-A / 4-B の可視テキストはいずれも input の前にあるため、後方テキストのケースが存在しない）。

**5. form / autocomplete は選定に影響しない**

6 系は 4 件すべて有効。**`autocomplete=off` でも充填されます**。form の内外も無関係でした。

**6. 誤爆はない**

0 系は 3 件とも無効。識別情報を持たないフィールドが巻き込まれることはありませんでした。

### 全ケース同時の場合との突き合わせ

単独では 21 ケースが充填可能であるにもかかわらず、全ケースを 1 ページに置くと **7-C だけ**が選ばれました。「1 回の Autofill につき 1 フィールド」という制約が改めて裏付けられています。

充填可能な候補（type ゲートを通過し、かつ単独で ✓）は次の 21 件です。

```
1-A 1-B 1-C 1-D  2-A 2-B 2-C 2-D 2-E  3-A 3-B  4-A 4-B  5-B  6-A 6-B 6-C 6-D  7-A 7-B 7-C
```

この中で 7-C が選ばれた理由の仮説は次のとおりです。

| 仮説 | 内容 | 現データとの整合 |
| --- | --- | --- |
| 位置ベース | 一致した候補のうち、読み込み時点の DOM 順で最後のものが選ばれる | 整合（7-C は候補中の最後尾。反転テストは走査キャッシュのため反証にならない） |
| スコアベース | 一致したシグナル数が多い候補が優先され、同点時の tie-break が DOM 順（後勝ち） | 整合（7-A/B/C のみ `placeholder` + `aria-label` の 2 つが一致し、同点最大となる） |
| 属性名ベース | `id` / `name` の辞書順で決まる | 整合（`dup_a` < `dup_b` < `dup_c` が DOM 順と一致してしまい区別できない） |

> [!IMPORTANT]
> **位置ベースとスコアベースは、現在のページ構成では同一の予測を出すため区別できません。**
> 最大値探索の比較を `>=`（非厳密）で書くと、同点候補のうち最後のものが選ばれます。7-A/B/C は 2 シグナルで同点最大、他の候補はすべて 1 シグナルなので、
> 「一致した最後の要素を選ぶ」実装でも「スコア最大＋同点後勝ち」の実装でも、結果は等しく 7-C になります。
> 分離するには、**スコアの高い候補をページ前方に配置する**必要があります（下記の実験 1）。

### 次に必要な実験

1. **スコアと位置を分離する** — `placeholder` + `aria-label` の 2 シグナルを持つフィールドを**ページ前方**（セクション 0 の直後など）に 1 つ追加する。前方の 2 シグナルが充填されれば**スコアベース**、後方の 1 シグナルが充填されれば**純粋な位置ベース**と確定します。これが最も情報量の大きい実験です（**未実装**）
2. **`?reverse=1` で辞書順説を検証する** — 1Password の走査前に順序が確定するため、走査キャッシュの交絡を受けません。ただし**位置ベースとスコアベースの分離には使えません**（反転時は 7-A がページ最後の input であると同時に、同点最大のうち最後でもあるため、両説とも 7-A を予測する）

   | 結果 | 言えること |
   | --- | --- |
   | `7-A` が充填 | 位置ベース or スコアベース（分離不可）。辞書順で後勝ちする説は棄却 |
   | `7-C` のまま | 属性名の辞書順で決まっている可能性が濃厚 |

3. **後方の可視テキストを拾うか調べる** — input の**後ろ**に、ARIA を伴わない素の `span` を置いたケースを追加する。4-A / 4-B（前方テキスト）が有効だったのに対し、後方でも有効なら近傍テキスト探索は前後双方向、無効なら前方限定と確定します（**未実装**。`aria-describedby` の可否はすでに 3-C で決着しているため、これはそれとは独立した問い）
4. **辞書順と DOM 順を食い違わせる** — 7-A/B/C の `id`/`name` を `dup_z` / `dup_m` / `dup_a` のように命名し、属性名ベース説を分離する（**未実装**。既存の観測結果との比較可能性を保つため、意図的に現状の命名を維持している）

> 上記は単発の観測結果です。再現時は 1Password 拡張機能・ブラウザ・OS のバージョンを併記してください。

- `FILLED_BY_1PASSWORD` はダミー値です。実際の認証情報をカスタムフィールドに入れて検証しないでください
