# 観測された挙動

[← README に戻る](../README.md)

1Password のカスタムフィールド `OP_TEST_TOKEN` を用いた検証の生の結果と、そこから読み取れることをまとめています。
外部ソースとの照合は [sources.md](sources.md) を参照してください。

## 実験 1: 全ケースを 1 ページに並べた状態での Autofill

**結果: `7-C duplicate #3` のみに値が入り、他の全フィールドは空のまま。**

読み取れること:

- 1 回の Autofill で充填されるのは 1 フィールドのみ。複数の候補がマッチしても 1 つに絞られる
- 選ばれたのはページ内で**最後**の input であり、かつ `placeholder` と `aria-label` の**両方**がマッチする唯一のグループ（7-A/B/C）の一員だった

## 実験 2: 「各セクションのDOM順を反転」後に再度 Autofill

**結果: 反転後も `7-C duplicate #3` のみに値が入った。**

反転によりセクション 7 の並びは 7-C → 7-B → 7-A となり、7-C は先頭、**7-A がページ最後の input** になります。
それでも 7-C が選ばれたため、「ライブ DOM 順で最後のものが選ばれる」という単純な位置ベース説は成立しません。

ただしこの試行には交絡があり、**説を棄却する根拠にはなりません**:

- 反転ボタンは JS で `appendChild` し直しているだけで、1Password はページ読み込み時にフィールドを走査してインデックスを保持している可能性が高い
- その場合、後から並べ替えても拡張機能側の認識は更新されず、「読み込み時の DOM 順で最後」のまま 7-C が選ばれ続ける

1Password 社員が「初回解析後に field type がキャッシュされ再解析されない」と述べており、この仮説と整合します（[sources.md](sources.md) 参照）。

## 実験 3: 単独モード（`?only=`）による属性別の判定

31 ケースを 1 件ずつ単独で実行した結果。**✓ = 充填された / ✗ = 充填されなかった**。

| ケース | 内容 | 結果 |
| --- | --- | :---: |
| 0-A / 0-B / 0-C | 識別情報なしの通常 input | ✗ |
| 1-A | `id` 一致 | ✓ |
| 1-B | `name` 一致 | ✓ |
| 1-C | `placeholder` 一致 | ✓ |
| 1-D | `title` 一致 | ✓ |
| 2-A | `label for` | ✓ |
| 2-B | label 内包 | ✓ |
| 2-C | 関連なし label | ✓ |
| 2-D | 壊れた `for` | ✓ |
| 2-E | 離れた `for` | ✓ |
| 3-A | `aria-label` | ✓ |
| 3-B | `aria-labelledby` | ✓ |
| 3-C | `aria-describedby` | ✗ |
| 4-A | `span` 直前 | ✓ |
| 4-B | `div` 直前 | ✓ |
| 4-C | CSS tooltip（`display:none`） | ✗ |
| 4-D | `hidden` テキスト | ✗ |
| 5-A | `textarea` + `placeholder` | ✗ |
| 5-B | `type=text` + `placeholder` | ✓ |
| 5-C | `type=search` + `placeholder` | ✗ |
| 5-D | `type=email` + `placeholder` | ✗ |
| 5-E | `type=password` + `placeholder` | ✗ |
| 6-A | form 内 | ✓ |
| 6-B | form 外 | ✓ |
| 6-C | `autocomplete=off` | ✓ |
| 6-D | `autocomplete=username` | ✓ |
| 7-A / 7-B / 7-C | 完全重複候補 | ✓ |

### 読み取れること

**1. 要素の型が「門番」として働いている**

5 系はすべて `placeholder="OP_TEST_TOKEN"` で識別情報が同一なのに、`type=text` の 5-B だけが充填されました。`search` / `email` / `password` と `textarea` は全滅です。
つまり型は**マッチのシグナルではなく、充填可能かどうかを決めるゲート**として働いています。`type` 属性を持たない 1-C（＝暗黙の `text`）が有効なこととも整合します。

**適用範囲**: 本結果は **Text（テキスト）種別**のカスタムフィールドを使用した場合のものです。1Password のカスタムフィールドには テキスト / URL / メール / 住所 / 日付 / ワンタイムパスワード / パスワード / 電話 / サインイン の種別があり、種別ごとに充填先の `type` が異なる可能性があります。他の種別は未検証です。

`type=search` に対応するカスタムフィールド種別は一覧に存在しません。`textarea` に対応する種別も明確ではありませんが、**住所**種別が対象とする可能性があります。

**2. ラベル探索の範囲は正式な関連付けより広い**

`id` / `name` / `placeholder` / `title` / `aria-label` / `aria-labelledby` に加えて、**関連付けが成立していないケースまで有効**でした。

- 2-C（`for` も内包もない単なる label）
- 2-D（`for` が存在しない ID を指す壊れた label）
- 4-A / 4-B（直前の `span` / `div` のテキスト）

DOM 上の正式な紐付けを辿っているのではなく、**近傍の可視テキストを拾っている**と考えられます。2-E（DOM 上は離れているが `for` は正しい）も有効なので、正式な関連付けも併用されています。

**3. 不可視テキストは対象外**

4-C（`display:none` の tooltip テキスト）と 4-D（`hidden` 属性）はいずれも無効。テキストの内容は一致しているため、可視性でフィルタしていると考えられます。

検証したのは `display:none` と `hidden` の 2 通りのみです。`visibility:hidden` / `opacity:0` / サイズ 0 / 画面外配置などは未検証です。

**4. `aria-describedby` はラベル情報源として使われていない**

3-C のみ無効。単独モードでの検証のため、他フィールドとの競合による取りこぼしではありません。

`aria-describedby` は ID による明示的な参照であり、採用されていれば参照先 span の位置に関わらず解決されます（3-B の `aria-labelledby` と同様）。充填されなかったため、ラベル情報源として扱われていません。

「ARIA を伴わない後方の可視テキストを拾うか」は未検証です。4-A / 4-B の可視テキストはいずれも input の前にあり、後方テキストのケースが存在しません。

**5. form / autocomplete は選定に影響しない**

6 系は 4 件すべて有効。**`autocomplete=off` でも充填されます**。form の内外も無関係でした。

**6. 誤爆はない**

0 系は 3 件とも無効。識別情報を持たないフィールドが巻き込まれることはありませんでした。検証したのは属性を持たない素の `input` 3 件のみです。

## 実験 1 と実験 3 の突き合わせ

単独では 21 ケースが充填可能であるにもかかわらず、全ケースを 1 ページに置くと **7-C だけ**が選ばれました。「1 回の Autofill につき 1 フィールド」という制約が改めて裏付けられています。

充填可能な候補（type ゲートを通過し、かつ単独で ✓）は次の 21 件です。

```
1-A 1-B 1-C 1-D  2-A 2-B 2-C 2-D 2-E  3-A 3-B  4-A 4-B  5-B  6-A 6-B 6-C 6-D  7-A 7-B 7-C
```

この中で 7-C が選ばれた理由の仮説は次のとおりです。

| 仮説 | 内容 | 現データとの整合 |
| --- | --- | --- |
| 位置ベース | 一致した候補のうち、読み込み時点の DOM 順で最後のものが選ばれる | 整合（7-C は候補中の最後尾。反転テストは走査キャッシュのため反証にならない） |
| スコアベース | 一致したシグナル数が多い候補が優先され、同点時の tie-break が DOM 順（後勝ち） | 整合（7-A/B/C のみ `placeholder` + `aria-label` の 2 つが一致し、同点最大となる） |
| 属性名ベース | `id` / `name` の辞書順で決まる | 整合（`dup_a` < `dup_b` < `dup_c` が DOM 順と一致してしまい区別できない） |

> [!IMPORTANT]
> **位置ベースとスコアベースは、現在のページ構成では同一の予測を出すため区別できません。**
> 最大値探索の比較を `>=`（非厳密）で書くと、同点候補のうち最後のものが選ばれます。7-A/B/C は 2 シグナルで同点最大、他の候補はすべて 1 シグナルなので、
> 「一致した最後の要素を選ぶ」実装でも「スコア最大＋同点後勝ち」の実装でも、結果は等しく 7-C になります。
> 分離するには、スコアの高い候補をページ前方に配置する必要があります（下記の実験 2）。

## 次に必要な実験

**1. カスタムフィールドの種別と `type` の対応**（コード変更不要）

1Password 側に メール / パスワード / 電話 / 住所 種別のカスタムフィールド `OP_TEST_TOKEN` を作成し、既存の `?only=5-D`（`type=email`）/ `?only=5-E`（`type=password`）/ `?only=5-A`（`textarea`）を実行する。

| 結果 | 言えること |
| --- | --- |
| メール種別で 5-D が充填される | 種別と `type` が対応している |
| どの種別でも 5-D が充填されない | `input[type=email]` は種別を問わず対象外 |
| 住所種別で 5-A（textarea）が充填される | textarea も種別次第で対象になる |

**2. スコアと位置の分離**（未実装）

`placeholder` + `aria-label` の 2 シグナルを持つフィールドをページ前方（セクション 0 の直後）に 1 つ追加する。

| 結果 | 言えること |
| --- | --- |
| 前方の 2 シグナルが充填される | スコアベース |
| 後方の 1 シグナルが充填される | 純粋な位置ベース |

**3. `?reverse=1` による辞書順説の検証**

読み込み時点で順序が確定するため、走査キャッシュの影響を受けにくい。位置ベースとスコアベースの分離には使えない（反転時の 7-A はページ最後の input であると同時に同点最大のうち最後でもあり、両説とも 7-A を予測する）。

| 結果 | 言えること |
| --- | --- |
| `7-A` が充填 | 位置ベース or スコアベース（分離不可）。辞書順で後勝ちする説は棄却 |
| `7-C` のまま | 属性名の辞書順で決まっている可能性 |

**4. 後方の可視テキスト**（未実装）

input の後ろに、ARIA を伴わない素の `span` を置いたケースを追加する。充填されれば近傍テキスト探索は前後双方向、されなければ前方限定。

**5. 辞書順と DOM 順の分離**（未実装）

7-A/B/C の `id`/`name` を `dup_z` / `dup_m` / `dup_a` と命名し、属性名ベース説を分離する。既存の観測結果との比較可能性を保つため、現在は元の命名を維持している。

外部ソースの突き合わせから浮かんだ追加候補（部分一致・`data-1p-ignore`・隠し input）は [sources.md](sources.md#突き合わせから追加したいテストケース) にまとめています。
